# ADR-0015: 中段治理——时点管线完整化 + 中间产物可视化 + pass 契约校验（draft）

- Status: draft（未立项设计输入，方向已明；落地起步 = 0.1.2 可视化管道）
- Date: 2026-09-08
- 承接: ADR-0007（pass 级时点已实现）；0007 明示"层内时点（analyzer 原语
  顺序 / transform 插件顺序）不在本决策范围"——**本 ADR 的深化目标正是该范围**。

## 背景

### 中段的自由度与缺失的反制（正反同源原则）

中段（analyze/transform）自由度极高：自定义原语/postpass/插件/黑板
（sym.attrs），组件可无限加语义、做变换。但缺少与自由度配套的**反制面**。

parser/linter 的分化是历史参照（非对称设计，是**困难驱动切分**）：最初想
做带错误恢复的递归下降解析器，太难（错误恢复分散在每个 production、恢复启发
式难调、恢复污染语义）——切成 ①精确 parser（遇错即停，只面对干净输入）+ ②
前置 linter（token 级复用同一语法 TOML 反向判定，边界靠错误显式化）。同源双
投影：一份语法描述投影出正向识别（parser）与反向判定（linter）。

中段对应物：需要"对加工产物的判定面"。现状盘点：

| 层 | 机制 | 判定对象 | 状态 |
|---|---|---|---|
| 输入侧 | TP 族检查（`_check.py` postpass error 阻断）+ L1 checks + linter | 用户代码合法性 | 已有 |
| 输出侧 | round-trip 幂等 / fidelity / sv-parser 对拍 | 变换后的文本/结构 | 已有 |
| **产物侧** | —— | 黑板/映射表/派生视图的加工产物 | **缺** |

产物侧缺口：没有机制盯着插件中间加工本身——postpass 写错形状的
`resolved_ports`、映射表来源断链、插件间依赖错位，无机制在写时拦或事后校验，
只会在消费端静默错或炸。→ 插件复杂后调试变难的根源。

### 为什么中段只能"事后校验"而非"前置 linter"

parser 能前置（单输入单消费：token 流入一个 parser，入口前可放筛子）。中段
是**链式多生产者**——后一个加工单元的输入是前一个的产物，无"所有加工前的单一
入口"，校验只能追着生产走：每段加工结束处（物化即校验）或分散在消费点（后者
= error-recovery parser 分散难调的老路，避免）。

## 决策（方向）

**统一模型：中段 = 一条可配置的时点线。pass = 状态从一个时点变到下一个时点后
形成的暂时阶段快照。** 三个能力都长在这条线上：

### 1. 时点管线完整化（承接 ADR-0007）

- 现状：pass 级时点（analyze/transform/check/custom + order/after + 命名
  schedule）已实现；analyze 内 postpass/原语、transform 内 slots 仍绑死阶段内
  固定顺序。
- 愿景：加工单元（postpass / transform 插件等）**也能声明时点**——如 typed_
  ports "展开在 analyze 主体后、check 前"，不被阶段绑定。时点序列器从 pass 级
  扩到单元级。
- 待定：什么被提升为一等时点单元（锚定层级），与"校验粒度作者自选"衔接。

### 2. 中间产物可视化管道（0.1.2 起步，先做）

- 时点 = 可视化断点：每阶段快照可 dump / 可追踪来源。已有点：symbols/ast dump
  （analyze 侧静态快照）；补：黑板变更日志（谁在哪个单元写了哪个键）、映射表
  来源追踪（`type_ports_flat[spi][slave]` 行来自哪条展开路径）、transform 侧
  中间产物（目前最薄，trans_callback 已删留空位）。
- 作用：分流调试复杂度（插件复杂后靠看中间态定位）。

### 3. pass 契约校验配置层（后做）

- 插件作者在独立加工单元声明 **produces（产什么）+ requires（需什么）** →
  引擎机械校验：可获取性 / 依赖满足 / 来源 / 形状完整（闸机：来源是否本管线
  产出、requires 是否已满足、产物是否完整）。
- **完全可选、附加**：为"放心"而用；不实现校验层也可。粒度作者自选——高需求
  加工加细校验，低需求不加或少加（可选纪律设施，LLVM AnalysisManager 式；非
  rustc 全量 query——那剥夺粒度自选）。
- 校验点：阶段检查点/物化即校验（每时点边界），非消费闸（分散读点防御=老路）。
- 声明归属：produces/requires/contract 声明在组件 TOML（语言知识就地），引擎
  只做机械核验——同 linter 复用语法、L1 声明式 checks 的姿态。

### 关系

时点 = 可视化断点 = 校验点 = produces/requires 锚；依赖校验 = 时点排序/满足。
校验层来源核验依赖可视化管道（先能追踪来源，才能验"产物来自声明的单元"）——
故可视化排前、校验层在后。

## 权衡

- **非 rustc 全量 query**：全量强制登记/通道化剥夺粒度自选，且改动面大（所有
  读点改通道）。选 LLVM AnalysisManager 式可选声明 + 出口/阶段校验。
- **非消费闸**：每个读点防御 = error-recovery parser 分散难调老路。选阶段检查
  点（物化即校验），下游只面对已判定可信产物。
- **不是为对称造设施**：演进叙事是"困难驱动切分"（linter 前例）。闸机价值 =
  把"插件产物判定"从分散消费点/每次 debug 集中到阶段判定面。**立项判据** =
  中段真的到困难阈值（出现第 3、4 个复杂插件、真撞调试墙）；未到前声明面可先
  以可选能力形式存在（零成本，不逼任何人用）。
- **粒度锚定未定**：pipeline pass / postpass / transform slots / 声明单元四层
  候选，待定。
- 与"不留向后兼容"无冲突：可选能力新增，旧自由黑板不迁移亦可。
