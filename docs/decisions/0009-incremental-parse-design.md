## 设计输入

### 一、文本 ↔ AST 双向映射（增量核心机制）

- 关键 = 双向映射：源文本任意位置 ↔ AST 结构。方向 1（文本→AST）是正常
  解析；方向 2（AST→文本 / 文本 diff→AST 节点）让"历史 AST + 文本变动"
  互相定位——增量解析的全部机制建立在这张双向映射上。
- 任意位置开始解析：不要求从文件头裸起。做法 = **从语法结构边界开始，
  补头补尾**——变更点不是字节/token 级孤立重扫，而是先沿结构定位到
  最近的完整语法单元边界，在单元内重解析、向两头补齐结构上下文。
- 历史 AST 的角色：从缓存取出旧树后，用 **AST 结构 + 句指针同步定位
  更新位置**——新文本的变动 diff 到旧树节点上，判定哪些节点失效需重
  解析、哪些可整棵复用（复用是增量的全部收益来源）。
- 边界诚实：同步定位要求文本变动**有限度**——结构/句子漂移太大（大块
  增删、结构重构、括号层级错位）时同步失效、效果劣于全量。**必须保留
  完整解析的回退路径**：增量只是加速手段，不改变接受域与结果，正确性
  永远以全量为准（可对拍校验）。

### 二、AST 缓存选址（两选项 + 取舍）

- 选项 A：系统盘 temp——语义上就是放临时产物的位置，零污染；缺点：
  有时丢缓存（系统清理/重启），跨会话命中率不可控。
- 选项 B：解析路径下 `.code_cache`——文件 AST 按**内容 hash 命名**；
  hash 相同 = 内容相同 = 可复用（内容寻址），文本变动后 hash 变 → 天然
  可比对；缺点：污染工作区（需 gitignore）、只读/共享目录不可写。
- 提纯：hash 命名解决的是**失效判定**（内容寻址：hash 即版本，命中即
  复用，无需 mtime/时间戳簿记）——与"放哪里"是两个正交问题：位置决定
  持久性与污染，key 设计决定正确性。

### 三、宏节点与增量解析一体（P3.6 × P3.2）

- 宏节点入 AST 与增量解析改动是**一体**的：增量 diff 要求 AST 结构与源
  文本结构对齐；"一刀切全展开"让展开体 AST 与源文本错位（无源位置），
  任何涉及宏的编辑都无法局部定位（P3.3 已述）。完整单元宏保留
  MacroCall 节点后结构边界与源文本对齐，增量才可能覆盖宏区域。
- 一体性的代价 = **卫生检查**（P3.6 形态分类：完整语法单元 vs 残缺
  片段——残留残缺宏只能原位展开，是结构一致性破口）；可能需解析器
  改动（P3.1 span 绑定 + 宏调用位/展开体位双 span 语义）。

## 业界实践对照（"如何确定实践比例"）

- 结论先行：业界**没有固定的"变化比例"阈值**；判据分两类，且都保留
  "增量失败 → 全量"回退：
  1. **结构锚定 + merge 校验**：变更点沿语法树/单元边界延展，重解析
     最小完整单元；新子树必须能与旧树剩余部分精确拼接（merge），
     拼不上 → 扩大范围或回退全量。
  2. **成本模型**：增量簿记/重扫成本接近全量时直接全量（不少解析器
     全量解析本身亚毫秒级，文件级重扫最省心）。
- rust-analyzer：`crates/syntax/src/parsing.rs` 的 reparse_or_parse（reparse
  与 full parse 的选择函数）+ `reparsing.rs`（增量重解析边界处理）——
  策略 = 能局部重解析则局部，否则整文件。见
  [reparsing.rs](https://github.com/rust-lang/rust-analyzer/blob/abb1301c/crates/syntax/src/parsing/reparsing.rs)
  与 [parsing.rs](https://github.com/Veykril/rust-analyzer/blob/4303e741de62ec9e1ebbcfbafee0ed52a92f0f2a/crates/syntax/src/parsing.rs)
- tree-sitter：增量解析 = 编辑后从受影响最内层节点重扫，LR 状态机自动
  决定范围、错误恢复兜底；无显式比例——编辑越小收益越大，编辑接近全量
  时成本自然趋近全量解析。见
  [Is it really incremental parsing?](https://github.com/tree-sitter/tree-sitter/discussions/3481)
  与 [DeepWiki: Incremental Parsing](https://deepwiki.com/tree-sitter/tree-sitter/2.4-incremental-parsing)
- 对 tpc 的含义：P3.2 的"延展到完整可重解析单元"已是结构锚定路线；
  应补 **merge 校验**（重解析结果与旧树拼接验证，失败 → 全量）为默认
  处置，而非追求普适比例；阈值类参数（如重解析范围 > 文件 X% 直接
  全量）留给实测标定（数据决策，非拍脑袋）。

## 补充想法（2026-09-02 反馈）

1. **缓存 key 必须含语法版本签名**：tpc 语法是配置（grammar TOML），
   语法文件变更会让旧 AST 失配——key = hash(源文本) 不够，须并上语法
   包指纹（引擎配置同）；否则增量结果与当前语法不一致 = 静默错误，
   比丢缓存危险。
2. **"从结构开始补头补尾"在 tpc 有现成资产**：parser 本就可从任意
   token 指针驱动（ParseContext 从边界起始 token）；block_start/end
   推导 + start_token_map + BoundaryChecker（P1.8 批次 3 引擎修复）都是
   现成的"找结构边界"机制——增量单元边界判定复用，不新造轮子。
3. **缓存分两级更稳**：L1 进程内（会话编辑历史栈，无 IO，最可靠）复用
   编辑前后树；L2 磁盘（.code_cache 或用户缓存目录）按 key 存整文件树
   供跨会话命中。"有时丢缓存"只损失 L2、L1 兜底后不再是问题——两选项
   不必二选一，可叠加。
4. **双向映射最小实现 = 节点持有源区间**（P3.1 tok_span 的反向应用）：
   "句指针"同步 = 编辑 diff（源区间）→ 命中旧树节点集 → 失效集 = 受
   区间影响的节点 + 父链上需重解析的结构祖先。P3.4 三类链传播是同一
   思路在语义层的推广（键 → 失效集）。

## 阈值解析式假设（2026-09-02 用户）

- "变动多大增量反超全量"是**纯数学问题**，比例很可能**有解析式**——粗估
  变动超过 20-30% 时增量耗时可能超过完整解析（簿记/边界常数 vs 变动
  规模的函数关系）。
- 验证计划：**下个版本发布时实测标定**——变量（文件 token 数 N、变动
  比例 r、单元边界簿记常数）扫参拟合反超点曲线，阈值落为可测参数
  （数据决策，延续"不拍脑袋"纪律）。
