# 协作行为范式（后来 session 必须继承）

> 从 `AGENTS.md` 迁出的**完整版**（2026-09-18：AGENTS 只留"必须先记住的"摘要 +
> 本文件指针；迁移依据见 `docs/references.md`「知名 AGENTS.md/指令文件范式调研」
> 的 💡 项"行为范式迁出、AGENTS 只留索引"）。制度文档，与门禁工具同层。

## 任务循环（作者 2026-10-09 定：每轮工作按此六步走）

1. **取任务输入**：作者的输入 + 已知缺口（`TODO.md` / `ROADMAP.md` / `docs/gaps/`）——
   一次循环只取**一个**能做到底的任务，不并行攒大改。
2. **复述核心约束**（每次循环先念一遍，防跑偏）：引擎**不留具体语言知识**、只保留
   **抽象通用模式**；具体语言能力**流入插件**；**AST 前**声明式解析闭环；**AST 后**
   插件能力驱动开放；**时点管线**编排；**可视化报告**输出。细节见
   `docs/engine_overview.md` + `AGENTS.md`「硬约束」。
3. **推进任务**：**先调研后计划，最后实现**；难题（多方案/影响面未知）先出调研与
   方案再动手。计划须含**预算**（性能/容量口径 + 超限处置）与**判据**（可执行形态，见下
   「循环执行细则」）；**改判定行为 / 碰契约面 / 影响面未知**的任务，**实现前**先让独立方
   **只对判据**搜反例（计划级证伪，省整类回退；实现后的对抗审计照做）。全程**留记录**
   （落档到该落的位置），**保持任务前后一致**——不许"狗头羊尾"（开头铺很大、结尾草草收）。
4. **独立测试 + 按影响范围收口**（作者 2026-10-11 调整）：先建**独立判据**单独验证本次改动；
   收口按**影响范围**取测试（受影响的目录 + 该轮动过的门禁），**不默认跑全量**；完整
   `pytest tests` 与长耗时门禁（如 `tools/check_gate_efficacy.py` 逐条变异）只在**跨子系统
   改动 / 发布收口**时跑。
5. **收口**：总结改动 → **声明缺口并找到缺口归属**（TODO / ROADMAP / gaps / DRAFT）→
   同步文档 → **删除完成项与废弃项** → 把改动**收为最小**（不做无关顺手改），防止项目
   无限膨胀。
6. **回到起点**：一次循环结束即回到 1，等下一个输入；循环记录以 `CHANGELOG.md`
   的对应条目为准（不另设流水账文件）。

**循环执行细则**（维护者按「决策权归属」自决落档，不改上面六步的语义）：

- **判据必须可执行**（步 3/5）：计划里的每条判据都要有能跑的形态——`tests/` 用例或
  `tools/` 探针命令，并写明期望的红/绿；只写在文档里的"同批判据"不算判据，只能算注记
  （反例：raw 的 A 类遮蔽有测试，B 类赋值链当时只有一句话，下一轮实现者拿不到验收形态）。
- **验证只读、按影响范围跑**（步 4）：验证/对拍脚本**不得写回工作树**——写回会与并发跑测试
  的成员互撞（实测造出 5 条假红）；A/B 对拍用 `tools/ab_pipeline_compare.py`（`git archive`
  到临时目录跑 PRE）。**测试范围 = 改动的影响面**（受影响目录 + 该轮动过的门禁）；全量
  `pytest tests` 与 `check_gate_efficacy` 只在跨子系统改动或发布收口时跑（作者 2026-10-11）。
- **"零可见变化"要给证据**（步 4/5）：声明本次改动用户不可见时，附对拍产物（逐文件
  rc / 渲染产物摘要相同）；拿不出产物就只能报 `partial`。
- **任务输入带溯源**（步 1）：**派生项**（由上一轮结论长出、而非作者点名或审计直接反例）
  在 TODO 里标 `来源：…`，收口时重过一遍"还值不值得做"，防派生链自激膨胀。
- **审计要给反例**（步 4）：独立审计/复审的产出必须含"构造了 N 个反例、其中 M 个不成立
  （附输入与命令）"；只报"已检查/无问题"的审计按 `partial` 计，不作为 `verified` 的依据。

## 决策权归属（作者 2026-10-09 明确授权）

- **框架级决策 → 作者拍板**：架构方向与引擎↔插件边界、语言包战略与支持范围、
  发布/推送/版本动作、跨子系统机制立项（要新建 ADR 的那类）、对外定位与措辞。
- **细节决策 → 维护者自决**（不必逐项回报）：实现形态与算法选型、判据与门限、
  边界接受/不做登记、文档归位与裁剪、工具与门禁细节、命名与文案。
- **自决不等于免记录**：仍守硬约束（语言知识不进代码 / 配置 fail-fast / 不留向后
  兼容 / 删除先证后删 / 先落档后动手 / 收尾分级），并把结论落到
  TODO·ROADMAP·`docs/gaps/`·CHANGELOG 的对应位置。
- **升级回作者的判据**（命中任一即先问）：① 要新增/改动引擎↔插件的**契约面或配置
  schema**（沿用已有机制、只补一个同族声明键的，按细节级自决）；② 要改对外承诺
  （发布、支持范围、README 定位）；③ 多方案取舍不可逆且成本未知；④ 作者点名参与。
- 本授权不改"收尾给结论分级 + 主动同步 TODO/ROADMAP"这两条固定环节。

## 克制推送

- 默认**只本地提交，不推送**。远程仓库是稳定的作品展示态，保持干净。
- 推送只在作者明确说"推"时执行；平时所有改动本地 `git commit` 攒着。
- 文档措辞保持中性工程化，不带"变现/领先/借鉴"这类指向性表述（公共历史里
  不留指向外部项目的显眼措辞）。

## 见贤思齐

- **先看成熟解法，用已验证的模式**：遇到问题先调研成熟产品（Verilator/slang/
  Verible/SpyGlass/svlint 等）如何解决同一个问题，尽量采用已经验证的模式
  （机制、语义、边界处置），不闭门造车重新发明——这是见贤思齐的前置动作，
  先看再定要不要抄、怎么抄。
- 调研外部项目时，**不拉踩开源作者**：先讲对方做得好、值得学的地方；差异用
  "各有取舍，非优劣"表述，不用评分式/压人式语气。
- **借鉴点标注层级**：🔥 直接借鉴 / 💡 启发 / 📌 路线观察；"不实现"也要写明原因。
- **对拍验证**：成熟工具的输出可作 oracle（sv-parser 差分、format 对拍等），
  用已验证实现校验自己的行为——与"先看成熟解法"互补：一个抄机制，一个当裁判。
- **先落档后动手**：调研/设计结论先按放置分流（见 `docs/README.md`「放置速查」）
  落档再立项实现，落档是动手的前置——不边做边定。

## 实施节奏（分步分期）

- 大任务**分步分期**，每阶段可独立验证（测试/门禁通过才进下一阶段），
  不攒大改一次性提交；阶段完成即提交并汇报。
- **先成因后动手**（借 Spec Kit 的 bug 流程三分离）：缺陷/异常行为先给**成因
  判定**（证据在哪、为什么是这个原因），再改，再验证；成因未定的修复不提交。
- **收尾给结论分级**（同上）：每次"修好了/做完了"必须带等级与依据——
  `verified`（有覆盖该行为的验证：测试/对拍/门禁实证）/ `partial`（只部分验证：
  仅手动探针、仅单层、未跑门禁等，**写明缺哪一环**）/ `failed`。缺验证不算
  完成，只能报 `partial` 并列出待验证项。
- **测试门禁 + 测后决策**：规则/改动过门禁（含真实语料实测量化误报）后
  按处置三选落地——修 / 降级 / 记录为已知边界；**回退只是处置之一，非
  必要**（过不了门禁才回退，结论照常落档）。
- **默认开/关是数据决策**：规则默认开关由实测误报面定——误报可接受就
  默认开（W 族先例），误报面大才默认关（NC/AW 先例），非固定策略。

## TODO/ROADMAP 维护纪律（两个文件都只留未完成）

- `TODO.md` 只列未完成待办，**完成项一律删除**（不保留 [x] 条目）——完成
  历史在 git log，决策记录在 references.md/ADR，TODO 不重复存。
- **短期待办在 `TODO.md`，中长期目标（backlog/非发布阻塞/v0.2 候选）在
  `ROADMAP.md`**；立项启动的项从 ROADMAP 移回 TODO，两文件同样完成即删。
  P 编号沿用原始编号（对应 git 历史与交叉引用），不重新编号。
- 每次"更新 TODO"动作必须**连带删除本次已闭环的条目**，不允许只加不减。
- **闭环即主动更新，无需作者提示**：每次任务收尾前主动同步 TODO/ROADMAP
  （删除本次闭环条目、立项项从 ROADMAP 移回 TODO），作为收尾固定环节，
  与代码改动一起本地提交。
- **调研/设计结论按"落档分流"落档**（见 `docs/README.md`「放置速查」），不进
  TODO/ROADMAP——两文件里的注记只允许"指明待办方向的上下文"，不允许沉淀调研结论。

## 指令文件自身纪律（AGENTS.md 修剪）

- 与代码同纪律：某条范式 agent 无指令也稳定执行 → 删（"已能正确做就删"，
  调研来源见 references.md「知名 AGENTS.md 指令文件范式调研」），不靠堆
  指令改行为——删除谓词 = 该范式不再需要被提示（与不留向后兼容同构）。
- **不复制门禁**：测试门禁/工具已强制的项（lint 风格、hardcode gate、测试
  命令等）不写进 AGENTS.md——一行"由门禁强制，修它报的"胜过重复条目，
  省上下文预算（文件保持 ~100 行量级）。
- **只用已成立或已明确同意的原则**（借 Spec Kit 的 constitution 纪律）：
  写 AGENTS.md 与本目录制度文档时不为填格式发明标准——不成立的标准是噪声。
- **细节迁出而非堆叠**：范式细节落本文件、命令与清单落就近 README
  （`tools/README.md`、`tests/README.md`），AGENTS.md 只留"必须先记住的"摘要
  与指针——AGENTS.md 是目录，不是百科。
